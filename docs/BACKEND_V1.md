# Genius — backend/security v1

## Главное правило

Ученик не предоставляет Genius email, номер телефона, ФИО, модель телефона, IMEI, серийный номер или данные других приложений. Для входа используется персональный одноразовый код, выданный учителем.

## Состояния подключения

1. Учитель создаёт персональный ключ.
2. На сервере сохраняется **только криптографический хэш** ключа.
3. Ученик вводит код.
4. Сервер проверяет хэш и создаёт `connection_request` со статусом `PENDING`.
5. До решения учителя учебные данные ученику не выдаются.
6. Учитель выбирает `APPROVE` или `REJECT`.
7. Только после `APPROVE` создаётся/активируется `student_id`, ключ помечается `USED`, а сервер создаёт защищённую сессию.
8. Повторно исходный ключ использовать нельзя.

## Минимальный API

- `POST /student/access/request` — принять код и создать PENDING-заявку.
- `GET /student/access/status/:requestId` — вернуть только статус заявки.
- `GET /teacher/connection-requests` — список заявок только для классов этого учителя.
- `POST /teacher/connection-requests/:id/approve` — подтвердить.
- `POST /teacher/connection-requests/:id/reject` — отклонить.
- `POST /auth/logout` — отозвать текущую сессию.

## Security requirements

- Все запросы только через HTTPS.
- Коды не логируются в открытом виде и не хранятся в D1 как plaintext.
- Сессионный токен хранится на сервере только как хэш.
- В браузер сессионный токен выдаётся через `HttpOnly; Secure; SameSite=Strict` cookie.
- Решение по XP, роли, классу и статусу пользователя принимается только сервером.
- Учитель не получает сведения о модели устройства, геолокации, файлах, контактах, сообщениях и активности вне Genius.
- Teacher/Admin endpoints требуют отдельной усиленной аутентификации и авторизации.
- Критичные действия (`APPROVE`, `REJECT`, `REVOKE_SESSION`, `CREATE_ACCESS_KEY`) пишутся в `audit_log`.
- Для endpoint ввода кода должен быть rate limit.
- PENDING-заявки должны иметь ограниченный срок жизни.
